# 0038 — The tray: Sentinel in the menu bar and the notification area

**Date:** 2026-11-11 · **Status:** Accepted · **Amends:** ADR 0034 (consent and the indicator)

## Context

The maintainer asked for Sentinel to live in the macOS menu bar and the Windows notification
area, showing the person at the machine its status and giving them controls: whether the agent
is connected and to which server, the remote sessions open now, a way to end one, and a way to
pause remote access. ADR 0034 left the consent prompt (SEC-23) and the session indicator
(SEC-24) Linux-only, failing closed on Windows and macOS, because the agent's service runs
outside the user's session there and can't put anything on their screen.

## Decision

- **`sentinel-agent tray`, one per signed-in user.** The same binary, run in the user's own
  session: from the Run key under HKLM on Windows, from a launch agent limited to Aqua sessions
  on macOS. `sentinel-agent install` adds the entry and `uninstall` removes it. A second tray
  for the same user exits at once (a per-session mutex on Windows, a lock in the user's
  temporary folder on macOS). There is no Quit item: the tray is how the person at the machine
  sees who is in.
- **A local Unix socket, never a network port (SEC-26).** The service listens at
  `%ProgramData%\Sentinel\tray\tray.sock` (Windows 10 1803 and later) or
  `/var/run/sentinel-agent/tray.sock`. On Windows the folder's permissions let only
  Interactive users (signed in at the machine, not over the network or as a service) open
  it, and not create or replace files there. On macOS anyone may open the file, and each
  connection's user is checked with `LOCAL_PEERCRED`: only root and the user at the console
  are served. The SEC-26 source check allows exactly this one `"unix"` listener. Linux has no
  tray and opens no socket: X11 prompts already serve the person at the screen (ADR 0034).
- **Lines of JSON, checked before they reach the screen.** At most 64 KiB a message, 64
  sessions, 512 bytes a string, no control characters; unknown fields and types are refused.
  The decoder is fuzzed. A tray that stops reading is dropped rather than slowing the agent.
- **What the tray shows.** The agent publishes its status on every change: connected or not,
  the server, the version, whether remote access is paused, whether remote desktop asks first,
  and the open sessions with who opened each and when (only when the local policy shows an
  indicator, SEC-24). The server now sends the user's name with terminal and container shell
  requests, as it already did for desktop sessions. The icon is grey and hollow when off, green
  when connected, red with a dot while someone is in, amber with two bars when paused, so the
  states differ by shape as well as colour. A notification announces each session as it opens.
- **Consent through the tray (SEC-23).** A question goes to every connected tray; the first
  answer decides and the others' dialogs are closed. With no tray connected, the agent falls
  back to the machine's own way to ask (X11), and with none of those it refuses, as before. The
  dialogs default to Don't Allow; on macOS they are `osascript` dialogs run as the user, so a
  question that goes away is closed by stopping the process.
- **Ending a session and pausing.** Ending a terminal or desktop session from the menu closes
  its stream with "The person at the machine ended the session." Pausing ends every open
  terminal, container shell and desktop session, refuses new ones with `policy_denied`, and
  tells the server the desktop is unavailable for that reason. Monitoring, alerts and
  everything else carry on. A pause is recorded in the state folder, so a restart doesn't undo
  it; only the tray resumes.
- **Native, without cgo.** Windows calls Shell_NotifyIcon, TrackPopupMenu and MessageBox
  through `golang.org/x/sys/windows`; macOS calls NSStatusItem and NSMenu through purego's
  Objective-C runtime, on the main thread, which `sentinel-agent` locks in an `init` function
  (the one place the code base has one, because only `init` runs early enough).

## Consequences

- The protocol, the agent's side, the tray's logic and the menus are tested on every CI
  runner; the Windows and macOS faces are compiled and linted on Linux, unit-tested where they
  have pure logic, and not yet tried on real machines (the QA checklist covers them).
- Anyone signed in at a Windows machine can answer a consent question or pause remote access,
  not only the user whose screen is shared. On a shared machine an admin who doesn't want that
  can leave `desktop_requires_consent` off and accept that pausing is available to whoever is
  at the keyboard. A policy switch to turn pausing off is a possible later addition.
- A tray that can't reach the agent shows "The Sentinel agent isn't running" and retries every
  5 seconds.
